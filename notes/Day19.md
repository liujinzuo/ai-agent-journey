## 二、发现一：示例单独不害，示例碰上死规则才害

A 和 B 的 system 完全相同，唯一的差别是 user 里那条示例还在不在：

```
消息：「订单 A12345 的快递三天没动，我要退款」
输出：{"order_id": "A12345", "issue_type": "物流", "refund_requested": true}
```

有这条示例 → 判 `null`；没有 → 判 `true`。

第一反应是「示例把它教窄了」。这个结论我写下去之后又加测了一步，被推翻了：**再补一条 false 示例**（「快递慢，我等着用」→ `false`），让示例从一条变两条、一正一反，结果**还是 `null`**。如果原因是「标准被教窄」，那给了反例就该修好——它没修好。

那就把两个变量都摆开，2×2 各测一格（同一条客户消息，温度 0）：

| | 不带示例 | 带示例 |
|---|---|---|
| **严格规则**（没明说就 null） | `true` | **`null`** |
| **放宽规则**（可合理推断） | `true` | `true` |

四格里只有一格坏掉：**「严格规则」和「示例」同时在场才出事**，各自单独都是好的。

准确的机制是两条分开起作用：

- **规则**决定默认怎么走。写了「没明说就 null」，它手上就多了一个随时能退的出口。
- **示例**给的是「合格答案长什么样」的实物。规则一死，示例就顶替规则成了判据：不像这条，退回 null。
- 规则放宽时那个出口没了，示例再规整也无处可退，照样判 `true`。

一句话：**示例不是教程，是放大器——它把规则的严格程度放大成手上的具体动作。**

（这条也修正了我当天早些时候说的「示例在教判断标准」：只对了一半。示例确实会改判据，但只有在规则本身已经写死的时候，它才有这个力气。）

## 三、发现二：D 为什么能两边都站住

D 做了两件事，缺一不可。

**第一，把松紧拆到字段上。** 不再用一句「没有明确写出的就填 null」管所有字段，而是每个字段各定各的：

```
order_id：必须能在原文里找到完整单号原文；找不到填 null，绝不允许补全或编造。
refund_requested：明确提出「要退/要退钱/要退款/要退货」填 true；
                  只抱怨、威胁投诉、追问进度但没提退款填 false；
                  完全没涉及退款才填 null。
```

注意 `false` 和 `null` 分开写了：**没提退款** 是 null，**提了但没要求退** 是 false。这一层区分，一句全局规则是表达不出来的。

**第二，要求先写一行依据，再给 JSON。**

```
依据：客户说"…订单号好像是 SF 开头的一串"，未给出完整单号，
      且"不给退我就去投诉"明确提出退款诉求。
{"order_id": null, "issue_type": "质量", "refund_requested": true}
```

这就是**思维链**（Chain-of-Thought）：让它把判断过程写在答案前面，而不是直接在答案里猜。你算 17×23 直接在脑子里报数容易错，打草稿就稳；模型也一样，**先输出推理，后面的结论是照着推理写的**。

三个副作用要知道：

1. **输出变长 = 花钱变多**，token 至少多一倍；
2. **格式变脏**，代码不能整段 `json.loads`，得只抓最后一个 `{...}` 块（脚本里的 `extract_json` 就是干这个）；
3. **依据可以被人核对**——这是好事。结论错了，你能一眼看出它是哪一步想歪的，而不是只看到一个错数字。

## 四、系统提示：规则放在哪一层

`system` 和 `user` 不是两个输入框，是两个层级。

| | 放什么 | 特点 |
|---|---|---|
| `system` | 岗位说明书：身份、规则、输出格式、禁止事项 | 每次请求都要重发一遍（模型不记得上次），优先级高 |
| `user` | 今天这一单的具体情况：客户消息、待处理数据 | 每次不同，是变量 |

三条实务：

1. **模型是无状态的。**`.env` 里的钥匙不会让它记住你；那句「以后回答短一点」也只活在这次请求里。所以 system 必须随每次请求重发——这就是为什么 API 调用比网页聊天贵：网页那边帮你存了上下文。
2. **system 不是保险箱。** 用户消息里写「忽略以上所有指令」，模型有可能真听。所以凡是要紧的规则（字段必须存在、枚举必须合法、不许编），**代码里还要再校验一遍**。脚本里的 `judge()` 就是这个角色，它不相信模型，只相信拿到手的 JSON。
3. **别把规则同时写在两处。** 一处写「必须是 JSON」，另一处写「用 markdown 表格」，模型会挑一个。规则只能有一份源。

## 五、什么时候用

| 场景 | 要不要思维链 |
|---|---|
| 简单抽取、分类、打分 | 不用，反而多花 token、多出解析麻烦 |
| 判断有歧义（像今天这种「算不算要求退款」） | **要**，让它先写依据 |
| 数学、多步推理、写方案 | **要**，效果差距最明显 |
| 要机器逐条核对的批量任务 | 要「依据」那一行，事后能查是哪里错 |

口诀：**规则按字段写，理由放在结论前。**
