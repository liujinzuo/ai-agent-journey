# Day14 · 按块算

> 一句话：**模型不是按「字」读你的话，是按「块」（token）读的——它按块看、按块记、也按块收钱。**

---

## 一、为什么今天要建直觉

前十三天，你写的每一行代码都能自己验证：跑一遍看结果对不对。

但模型不是这样。它是一坨几百亿个数字，没人能"打开看看里面"。所以你必须先建立几个**直觉**——大概知道它怎么读、怎么记、哪里会错。没有这几个直觉，你写的提示词就是碰运气。

今天只建两个直觉：**它怎么读（token）**、**它能记多少（上下文窗口）**。

---

## 二、生活里的场景：书是按「页」算的

图书馆不按「字」管书，按「页」编号、按「架」摆放。

你借书时不能说"我要借 3000 个字"，只能说"借 10 页以内的一段"。模型也是这样，它不管你有多少字，管你有多少**块**。

**token 就是它的「页」。** 念「偷肯」。

一个 token 大约等于：

- 英文：4 个字母，比如 `weather` 大概是 2 个 token
- 中文：1~2 个字，比如「北京」大概是 2 个 token

**注意：不是精确等于。** 这是估算，真实值每个模型都不一样。

## 三、跑一遍，看差距

```powershell
cd C:\Users\22155\ai-agent-journey
.venv\Scripts\python.exe -X utf8 code\day14_tokens.py
```

前两段输出（我本机实测）：

```
【中文 10 个字】
  原文： 北京明天天气怎么样呀
  字符数： 10    字节数： 30    token 估算： 15

【英文 10 个词】
  原文： How is the weather in Beijing today my friend
  字符数： 45    字节数： 45    token 估算： 11
```

只看这两段，就有一个反直觉的结论：

> **中文 10 个字（30 字节），比英文 45 个字母（45 字节）更贵。**

字节数是 30 对 45，看着中文便宜；但 token 是 15 对 11，中文反而贵。

为什么会这样？因为**中文常用词的切分效率低**——模型看到「北京明天」这串字，得切成好几块；而 `Beijing` 这种高频词，往往一块就够了。

这三件事的实际影响：

1. **花钱**：API 按 token 计费，同样的意思，中英文价钱能差一倍。
2. **速度**：token 越多，它生成得越久。
3. **记性**：token 越多，占的窗口越大，能记住的内容越少。

## 四、上下文窗口：一次能看多少块

模型没有"记忆"，它每次回答时，只是把**这次给你的全部内容**从头读一遍。

这个"全部内容"有上限，叫**上下文窗口**（context window）。

打个比方：

> 你有一个只能放 60 张纸的文件夹。
> 每说一句话，就往里放一张纸。放满了，最老的那张就被挤出来，**再也不会被看到**。

它不是"忘了"，是**根本没再被读**。

---

## 五、跑一遍，看它挤出去

同一个脚本的下半段：

```
加了第 1 轮后：窗口里 1 条，共 17 token
加了第 2 轮后：窗口里 2 条，共 34 token
加了第 3 轮后：窗口里 3 条，共 51 token
加了第 4 轮后：窗口里 3 条，共 51 token  <- 挤出去了 1 条最老的
加了第 5 轮后：窗口里 3 条，共 51 token  <- 挤出去了 1 条最老的
...
```

第 4 轮开始，每次加新消息，就有 1 条最老的被挤出去。到第 8 轮，**第 1、2 轮说的话已经在窗口外了**——对模型来说，那两句话等于从没说过。

这就是两个常见现象的根源：

| 现象 | 真实原因 |
|---|---|
| 聊久了它忘掉开头 | 开头被挤出窗口了 |
| 你纠正过它，它过几轮又犯 | 你的纠正被挤出去了 |

**对 Agent 来说这是核心问题**，因为 Agent 的对话比你聊天长得多：每次调工具都要把历史重发一遍，几十轮就跑满了。所以真实 Agent 都有"裁剪历史"或"定期摘要"的代码——不是优化，是必须。

## 六、顺便说清"幻觉"

模型本质上做一件事：**根据前面的内容，猜下一个 token 最可能是什么**，猜完再猜下一个，一个字一个字往外蹦。

它没有"查证"这个动作。所以当它不知道的时候，它不会停下来说"我不知道"，而是**猜一个看起来很像的答案**继续往下崩。读起来通顺、自信、甚至格式工整——但内容是编的。

这跟它"不老实"无关，是它的工作方式决定的：**它天生只有"猜"，没有"查"。**

你以后学的工具调用、检索、Pydantic 校验，全都是在给它补"查"这个动作。

---

## 七、今天两个新名词

1. **token** —— 模型的计价和计量单位，念「偷肯」。大约英文 4 字母 / 中文 1~2 字。**不是字，也不是字节。**
2. **上下文窗口** —— 一次能读进去的 token 总量上限。超出的部分不会"记不住"，而是**根本没被读**。

> 今天不讲 temperature、top_p、embedding。这些以后用到再说。

## 八、验收

一道题：

> 你写了一个客服机器人，用户跟它聊了 200 多轮之后投诉：「我第一句话就说了我是VIP，它后来完全不认了。」
>
> 按今天学的东西，最可能的原因是什么？

**答：上下文窗口满了，第一句话被挤出去了。**

200 多轮对话远超一个窗口能装下的量，第一句「我是VIP」早就在某一轮被推出去了。模型不是"不认"，是**根本没读到**——它手里没有这条信息。

### 一个要分清的地方：这不是幻觉

「记住不住」和「幻觉」是两件不同的事：

| | 发生了什么 | 典型表现 |
|---|---|---|
| **窗口挤出** | 信息在，但没被读进去 | 「请问您是普通用户还是VIP？」——它在诚实地说不知道 |
| **幻觉** | 信息根本不存在，它编了一个 | 「您的VIP等级是金卡，2024年6月到期」——全是编的 |

前者的原因在**你的代码**（历史没管好）；后者的原因在**模型的工作方式**（只有猜，没有查）。混在一起会让排查方向跑偏：窗口问题要靠改代码解决，靠换更大的模型只能拖延。

### 正确的修法：关键信息不交给对话历史

VIP 身份这种「必须一直有效」的信息，不该和普通聊天混在一条滚动队列里。两种做法：

1. **放进系统提示词**（system prompt）——每次请求都随最前面一起发，永远在最前，不会被挤掉。
2. **每轮重新注入**——从数据库查出用户等级，拼在每轮消息里，而不是指望模型记得。

一句话：**重要的东西每次都给，不要指望它记得。**
