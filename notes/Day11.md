## 零、生活里的场景

你带了个实习生，让他帮你整理这周的支出。

**版本一**：你丢给他一张纸条，写「帮我整理一下这些支出」。
他可能会给你写一篇文章，可能做个饼图，可能按金额排序，可能给你提建议省点钱。每种都不一定是你想要的。

**版本二**：你说——
「你是财务助理。把这 6 笔支出整理成表格。不要解释、不要开场白、别自己加项目。用 Markdown 表格，两列：用途、金额（元），金额保留两位小数。」
他会照做，而且**每次照做都一样**。

**两个人干同一件事，差别只在你说了多少。**

一句话记住今天：

> **模型不会读心。你把要求说到多细，它就能做到多准。**

你会看到的差别大致是：

| | A（随手一句话） | B（四件套） |
|---|---|---|
| 开头 | 可能有「好的，我来帮你整理」 | 直接表格，没有废话 |

| 再试一次 | 结果可能跟上次不一样 | 结果**基本一样** |

**最后一行最关键：稳定。** 写程序最怕「这次和那次不一样」。

## 二、四件套

一段好用的提示词，拆开就四样东西：

```
1 你是谁（角色）     → 你是财务助理。
2 干什么（任务）     → 把下面 6 笔支出整理成表格。
3 不许什么（约束）   → 不要解释、不要开场白、不要自己加项目。
4 给我什么样（格式） → Markdown 表格，两列，金额保留两位小数。
```

写提示词时逐项检查，四样齐了再发。这比背任何「提示词技巧」都有用。

注意第 3 条的作用：**模型的默认行为是「多说一点」**。你不写「不要解释」，它就会解释；不写「不要加项目」，它就可能好心补一句「本周共 180 元」。这些对人挺贴心，对程序是灾难。

## 三、为什么「输出格式」是 Agent 的命根子

跟人聊天，格式不重要——你看得懂就行。

**跟程序合作，格式就是全部。** 你的程序拿着模型的回答，下一步是把它当数据用：取字段、存数据库、传给下一个函数。

只要模型多一句「以下是整理结果：」，你解析 JSON 的代码就会当场报错。

所以真实 Agent 里，提示词永远会把格式写到近乎啰嗦的程度，比如：

```
只返回 JSON，不要任何其他文字。
结构：{"city": "城市名字符串", "days": 天数整数}
不要 markdown 代码块，不要解释。
```

**然后接一道检查关口**——这就是你 Day9 学的东西：

```
提示词要求「只返回 JSON，days 是整数」
        ↓
模型返回一段话
        ↓
程序先用 json.loads 解析，再用 WeatherArgs 检查
        ↓
通过 → 拿去干活
不通过 → 把报错回给模型：「你没按要求返回，days 不是整数」，让它重来
```

**提示词负责「尽量不出错」，Pydantic 负责「出了错能发现、能说清」。两者缺一不可，缺一不可。** 只靠提示词叫祈祷，只靠检查叫碰运气。

## 四、今天的两个新名词

1. **Prompt（提示词）** —— 你给模型的那段话，全部。念「普朗普特」。
2. **四件套** —— 角色 / 任务 / 约束 / 输出格式。写提示词时的自检清单。

## 七、验收

一道题：

> 你希望模型**每次**回答都用同样的格式，好让你的程序能直接读取、不用你手工改。
> 四件套里最该写清楚的是哪一件？

- **A.** 角色（你是谁）
- **B.** 任务（干什么）
- **C.** 输出格式（给我什么样）
- **D.** 约束（不许什么）

答：**C（输出格式）。**

第一次答的是 D（约束），抓到一半——「不要解释、不要开场白」确实也是保格式稳定的一招。但决定**形状**的只能是第 4 件：

| | 正面清单：要什么样 | 负面清单：不许干什么 |
|---|---|---|
| 第 4 件 输出格式 | 两列、列名叫「用途」「金额（元）」、金额保留两位小数、Markdown 表格 | — |
| 第 3 件 约束 | — | 不要解释、不要开场白、不要自己加项目 |

拿装修打比方：**输出格式是图纸，约束是「别乱加装饰」。** 只给「别乱加装饰」这一句，师傅还是不知道要做成什么样。

约束能治「多说话」，治不了「说错形状」——「不要解释」没法告诉模型金额该写 `12` 还是 `12.00`，也管不了两列还是三列。
